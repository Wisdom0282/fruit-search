Search that answers while you type.

A predictive fruit search with plain JavaScript at its core, no framework, and motion added with CSS and GSAP. It works with a keyboard and a screen reader, and it respects reduced motion. Try it first, then read how it’s built.

    Use ↑ ↓ to move, Enter to choose, Esc to close.

    The story

    The brief

    Build a small search app that suggests fruit as the user types. The assignment was to practice DOM manipulation, array methods and ES2015 features. I treated it as a chance to build something small and make it feel finished.

    The problem

    Autocomplete looks easy until you use one. It has to rank results sensibly, highlight what matched without breaking on odd input, stay usable without a mouse, and announce itself to assistive tech. Most tutorial versions skip all four.

    The approach

    I kept the logic as small pure functions (rank, highlight) and left all state in one object, so each piece can be read and tested on its own. Rendering happens in a single place, driven by that state. Motion sits in a separate layer on top, so removing it never breaks the search.

    1. InputUser types; the input event fires.
    2. RankFilter and sort the fruit list.
    3. RenderBuild the list with DOM nodes.
    4. SelectClick or Enter fills the field.
    Stack
    HTML, CSS, JavaScript (ES2015+), GSAP
    Dependencies
    GSAP and ScrollTrigger for motion only; the search logic uses none
    Motion
    CSS animations, scroll-driven animations, GSAP timelines
    Accessibility
    ARIA combobox pattern, live status, visible focus, reduced motion
    Concepts
    Event delegation, DOM construction, array methods, regex escaping

    Decisions worth a look

    Ranking beats plain filtering

    Typing “an” should surface Ananas-style prefix matches before “Mango”. Prefix matches go first, then alphabetical.

    rank()

    const rank = (query) => {
  const q = query.trim().toLowerCase();
  if (!q) return [];
  const starts = (name) => name.toLowerCase().startsWith(q);

  return FRUITS
    .filter((name) => name.toLowerCase().includes(q))
    .sort((a, b) => starts(b) - starts(a) || a.localeCompare(b));
};

    Highlighting without innerHTML

    Building nodes with textContent means user input is never parsed as markup, and a regex escape keeps characters like ( from crashing the search.

    highlight()

    const escapeRegExp = (s) => s.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");

function highlight(name, query) {
  const frag = document.createDocumentFragment();
  const match = new RegExp(escapeRegExp(query.trim()), "i").exec(name);
  if (!match) return frag.append(name), frag;

  const mark = document.createElement("mark");
  mark.textContent = match[0];
  frag.append(
    name.slice(0, match.index),
    mark,
    name.slice(match.index + match[0].length)
  );
  return frag;
}

    One listener for every suggestion

    Suggestions are recreated on every keystroke. Attaching a click handler to the list and reading event.target avoids rebinding hundreds of handlers. 

    list.addEventListener("click", (e) => {
  const item = e.target.closest("[role=option]");
  if (item) choose(Number(item.dataset.index));
});

    Accessible by construction

    The input uses the ARIA combobox pattern: aria-activedescendant tracks the highlighted option while focus stays in the field, and a visually hidden live region reports how many results are available.

    Motion and interaction

    Motion here has one job: show what changed. The page uses three tools, each for the kind of motion it handles best.

    CSS animations
    The dropdown opening, link underlines, button press, and a border that follows the cursor on the demo card.
    Scroll-driven animations
    The reading-progress bar at the top and the section reveals, using animation-timeline with no JavaScript.
    GSAP and ScrollTrigger
    The hero sequence, the staggered pipeline steps, the active nav link, and the confirmation when you pick a fruit.
    Reduced motion
    Every animation switches off when the visitor’s system asks for less motion.

    Scroll-driven, without JavaScript

    The progress bar is tied to scroll position by the browser, so it stays smooth even when the main thread is busy. Browsers without support skip the block and simply show the page.

    styles

    @supports (animation-timeline: scroll()) {
  @media (prefers-reduced-motion: no-preference) {
    .progress {
      animation: progress-grow linear both;
      animation-timeline: scroll(root);
    }
    @keyframes progress-grow { to { transform: scaleX(1); } }
  }
}

    GSAP for choreography

    CSS is ideal for single effects. When several things must run in sequence, a GSAP timeline is easier to read and adjust. It runs inside gsap.matchMedia(), so reduced-motion visitors never get it. 

    gsap.timeline({ defaults: { ease: "power3.out" } })
  .from(".bar", { y: -16, opacity: 0, duration: 0.6 })
  .from(".word-inner", { yPercent: 110, duration: 0.9, stagger: 0.08 }, "-=0.3")
  .from(".lede", { y: 16, opacity: 0, duration: 0.7 }, "-=0.5")
  .from(".demo", { y: 24, opacity: 0, duration: 0.7 }, "-=0.45");

    What I’d do next

    I stopped where the project was complete, but these are the next steps I would take:

    Framer Motion by porting the list to React and using layout animations, so results slide into their new order instead of being replaced.

    Fuzzy matching so “aple” still finds Apple, using edit distance with a small cap.

    Unit tests for rank and highlight, which are already pure and easy to test.

    Remote data with debounced requests and AbortController to cancel stale ones.

    What I learned: most of the quality in small UI is in details nobody sees: input edge cases, focus, announcements, and knowing when not to animate.
